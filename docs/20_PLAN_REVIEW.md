# 20｜规划复审：先把会议录音做好

审查日期：2026-09-28。范围：交接规格、阶段提示词、需求与验收矩阵、数据契约、辅助脚本；本轮不实施 M0。

**结论：技术方向可以保留，首版功能应收缩，录音可靠性的几处约定需要补实。** 不建议重写技术栈，也不建议先做项目知识库或本地 AI。第一份真正有用的交付应是：选来源、明确是否录自己、开始、停止，然后得到能直接听和手动上传的完整音频。

此文保留首次审查时的依据与建议。用户随后已明确采纳，现已同步至里程碑、AGENTS、验收矩阵、开发提示词和相关规划；当前执行标准以这些修订文件为准。工程环境准备见 `21_ENGINEERING_SETUP.md`，不表示录音软件已经实现。下文“本轮”及行号描述首次审查时的历史状态，后续文件行号可能变化。

## 1. 最值得调整的六项

### A. 日常入口再简单一些

依据：[产品需求](H:/AI/ProjectEcho/docs/01_PRODUCT_REQUIREMENTS.md:7)、[录音界面](H:/AI/ProjectEcho/docs/09_UI_UX.md:7)、[现有闭环](H:/AI/ProjectEcho/docs/12_MILESTONES.md:19)。

当前清单容易被实现成开会前必须选项目、填会议名、看进程树、做试录。建议默认“未分类项目 + 日期时间会议名”，录后再归档；首页突出会议来源、录制范围、麦克风开关、两路电平、开始/停止。进程树和 PID 放到详细信息，内部仍须真实验证，不能按 Zoom/Webex 名称猜来源。

10 秒试录保留为用户主动按钮，首次使用或来源变化时突出提醒，不要求每场重复走完整向导。来源和 mic 状态每场都要明确展示；mic 默认关闭。三类书签先合成一个“标记此刻”，分类以后补。已验证来源偏好可保存，不能持久复用旧 PID 或静默换麦克风。

### B. 把首版导出收敛成两个动作

依据：[导出最低要求](H:/AI/ProjectEcho/docs/06_MIX_EXPORT.md:24)、[导出界面](H:/AI/ProjectEcho/docs/09_UI_UX.md:26)、[M2 提示词](H:/AI/ProjectEcho/prompts/03_M2_MIX_EXPORT.txt:1)。

建议默认只有“播放完整录音”和“导出供转写”。停止后自动生成完整混音；上传副本按预设大小/时长分片，实际字节检查、尾段完整、重叠和时间映射保留。高级设置才展示格式、上限、重叠等参数。

目前产品需求/提示词要求 MP3、M4A、WAV 全部支持，导出规格又给出“WAV + 至少一种压缩格式”的最低标准。建议统一为 WAV + 一种经验证的默认压缩格式作为首版门槛；第二种压缩格式如果同一编码器即可低成本完成，可以一起交付，但不让它阻塞日常可用。

延后范围剪辑、删除暂停、自动寻找语音切点、诊断 stereo 的普通用户入口、响度调节界面和术语管理。首版保留完整时间轴，暂停填静音。若需要敏感区间处理，先做保留时长的静音副本，避免发展成剪辑软件；原音始终保留。延后编辑功能不等于删掉原始时间戳或基本分片映射。

### C. 保留一个采集进程，延后数据库和通用框架

依据：[架构](H:/AI/ProjectEcho/docs/03_ARCHITECTURE.md:9)、[存储](H:/AI/ProjectEcho/docs/11_STORAGE_SCHEMA.md:9)。

CaptureHost、分块写盘、恢复日志和 UI 失联后停采，都直接服务录音可靠性，建议保留。首版的会议列表可由 meeting.json 建立内存索引，SQLite 等到全文搜索/跨会议查询确有需要时再加。导出用一个可取消、可重试的后台任务即可，不预建插件系统、通用任务调度平台或多个空 worker 项目。

同步处理也按证据推进：从第一天保存实际 device/QPC 时间戳、帧数和中断信息，先做最小可验证映射。用两小时实验决定纠正算法的复杂度；未达标就修正或明确限用，不能把缺少测量当成不需要纠正。

### D. 补清停止、暂停和关闭麦克风的边界

依据：[暂停/停采约定](H:/AI/ProjectEcho/docs/04_AUDIO_ENGINE.md:15)、[尾音标准](H:/AI/ProjectEcho/docs/04_AUDIO_ENGINE.md:29)。关联 R07/R08/R09/R12，T11/T13/T15/T26。

“清空待丢弃缓冲”尚未明确哪些数据可丢。若实现者在 Stop 时直接取消整个队列，可能丢掉已经采集、还没写入的最后几个包；“最后 5 秒可听”不能充分发现最后几十毫秒的损失。

建议采集线程为 Stop/Pause/MicOff 定义并记录可验证的生效时间。正常 Stop 必须保存有效截止边界前的数据，完成队列写盘与文件收尾，再报告已保存。暂停和关 mic 要停止对应采集，边界后的数据不得进入保存文件；关闭完成前界面显示正在关闭，不能先显示已关。跨边界包的处理规则也要明确。

补合成测试：随机包位置停止、跨 30 秒文件边界停止、重复 Stop、mic-off 与写盘积压同时发生；检查末帧/短标记，而不只听文件大致有声音。这是规划缺口，目前没有实现可供认定为程序缺陷。

### E. 数据契约还不足以指导可恢复同步

依据：[时间信息要求](H:/AI/ProjectEcho/docs/04_AUDIO_ENGINE.md:9)、[meeting schema](H:/AI/ProjectEcho/schemas/meeting.schema.json:67)、[接口草案](H:/AI/ProjectEcho/reference/AudioContracts.cs:22)。关联 R08/R10/R11，T20/T22/T23/T24。

规格要求按 segment 保存格式变化、设备位置、QPC、flags 和时钟映射；当前 meeting schema 只有 source 级 format 与 chunk 的起点/时长/帧数。接口草案有部分瞬时信息，但还没有可落盘的 segment/index 契约。文档允许 sidecar，故这不是“绝对存不了”，而是关键存储约定尚未给出，不能把现有 schema 当完整实现合同。

M0/M1 应补一个小而明确的 sidecar 格式及示例：segmentId、格式、共同时间基准、原始时间戳/帧数/flags、chunk 引用、记录顺序与恢复有效边界。先证明录完退出后，仅靠磁盘文件仍能还原单轨和双轨时间轴；不要依赖进程内尚未丢失的状态。无须现在扩展全部转写/分析 schema。

### F. 首个可用版必须包含便携包和日常运行验证

依据：[M2/M6](H:/AI/ProjectEcho/docs/12_MILESTONES.md:7)、[T46/T49](H:/AI/ProjectEcho/tests/acceptance.csv:47)、[当前发布脚本](H:/AI/ProjectEcho/scripts/Dev.ps1:46)。关联 R21/R23。

M2 叫“首个可用版”，但无预装 SDK/.NET 的便携验证在 M6。建议 M2 就产出包含 CaptureHost、运行时和编码器的完整文件夹，做干净 Windows 的启动、录音、回放、压缩导出验证；依赖来源和分发许可随这次交付核对。当前脚本明确只发布 App，不能把它运行成功当完整打包成功。

锁屏、睡眠后的明确缺口/恢复行为，以及录音期间本程序播放旧录音导致回录，也要在日常使用前测。最简单的首版规则是录音期间禁用本程序回放；不需要先实现复杂播放路由。不能静默改变全局电源设置。M6 保留更广的发行回归，M3/M4/M5 都不是 M2 交付前置。

现有 T24 已把两小时同步测试放在 M1，这是正确的，应保留，并非所有可靠性测试都排晚了。

## 3. 两个容易影响实际体验的小补充

**看得出是否真的录到了。** 计时器、捕获连接状态、最近保存时间应分开。有效静音包、尚未观察到声音和明确设备/进程故障不能都显示成同一个绿色成功状态；也不能仅凭长时间安静判定失败、自动停录或扩大录制范围。建议先让用户通过主动试录确认来源，再持续显示客观健康信息。关联 R05/R06/R08/R09。

**按原始轨预算磁盘，而不是按上传 MP3 预算。** 例如两路都为 48kHz float32，远端双声道加 mic 单声道，原始数据约 2.07GB/小时（十进制，不含混音、索引和临时文件）；这只是算例，实际依协商格式计算。预检应展示预计占用并给导出预留空间。耳机作为默认推荐用法，不把独立麦克风等同会议软件处理过的声音；首版先不自研回声消除。关联 R07/R08，T18/T21。

## 4. 技术路线核对

本轮公开官方资料仍支持当前候选，不建议为了缩小范围换技术栈：

- .NET 10 是 LTS；具体 SDK patch 在开发阶段锁定。[Microsoft 支持表](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)
- NuGet 当前稳定 NAudio 为 3.1.0，面向 net9.0 及以上；仍需以实际构建确认所用接口。[NuGet 官方包](https://www.nuget.org/packages/NAudio)
- process loopback 的边界是进程及其子进程，官方 sample 要求 build 20348+；这不证明 Zoom/Webex 在本机已可录。[Microsoft sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/)
- GetBuffer 提供帧位置和 100ns 单位 QPC 时间，但选定封装是否暴露它们仍待 M0 验证。[Microsoft API](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)
