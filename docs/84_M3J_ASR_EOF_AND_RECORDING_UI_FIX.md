# 84｜M3J Lite：逐段时间异常保全与录音界面修复

2026-10-05，开发与验证进行中。版本按用户指定为M3J Lite，继承M3I；主目录M5C产品代码和已交付包保留，待本轮Lite验收后按既有授权同步。迁移清单见[83](83_M3I_TO_M5C_SYNC_CHECKLIST.md)。

## 现场确认与新失败

用户在Windows10复测后报告录音启动失败不再复现，长录音后处理明显加快。新脱敏Log进一步记录：ProcessTree、mic关闭，2475.325秒录音StorageComplete=True，本场处理33715ms。这是本场/用户复测范围的通过，不替代双轨同步、所有设备或干净Windows验收。

新识别失败与此前零时长不同：模型正常退出0，原始SRT/JSON完整348段且文字/原起止全部对应；只有原始最后第348段（旧分句后第184段）结束估计2476240ms，超过保存校验时长2475326ms共914ms。最后一个词token也越界，不是只多出结束控制token。

实际16k输入39605202帧，精确2475325.125ms；48k混音118815607帧，2475325.145833ms。输入/attempt、混音/render及render对清单/索引的SHA绑定均相符，RIFF/data到真实EOF，重采样差20.833微秒，不能解释914ms异常。用户省略了remote原轨，因此没有声称重新通过原轨全链校验。

这不是整篇字幕统一延迟914ms的证据，不能把全部字幕前移。模型时码是估计，单纯把250ms改成930ms/1秒仍可能再次失败。

## 最终修复原则

用户进一步要求考虑倒数第二段和多段越界，M3J从“仅原始最后一段”扩展为**逐个原始正时长越界段**处理，不要求异常在末尾。所有原始身份/正文/非负正向/绝对时长上限先通过结构校验。

- 完整JSON/SRT对应后，只有该段自己的全部词token能拼回全文、正长度且单调、全部落在其开始至真实音频范围内，才使用真实末词结束时间；不借相邻段，不按字数插值。
- 缺失/损坏/不匹配JSON、词时间跨EOF等不能证明时间时，只将相应段保存为untimed，全文和顺序保留，正常段照常分句/回听。起点已在EOF或之后的正时长段明确无可回听范围。
- 倒数两段、连续多尾段、中间越界后还有合法段、全部正向越界都不应因为这些局部时码异常丢掉整场文字。
- 保留原有仅最终原段、音频内开始且≤250ms的小幅处理兼容；防止分句把它再次扩成多个非法子句。没有增大固定容差。
- 手动导入不放宽；负数、反序、绝对超限、无效正文等结构错误仍拒绝，不伪造时间/文字。
- 单版最多100条越界细节及总数，10001段也须保全重开。原SRT/JSON/输入音频和人工稿不变。

有untimed文字时，TXT和完整JSON可导，正常部分可回听；SRT/VTT仍禁止静默漏字。真实识别成功、全部时码可用、人工确认正确三个状态不混为一谈。
