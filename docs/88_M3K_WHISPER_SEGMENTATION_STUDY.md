# M3K Lite（2026-10-06）分句调查与修复

用户本轮随后将版本名更正为 M3K。下文 `.local/M3J-20261006/` 是更名前已生成的证据目录，保留不移动；它不代表最终交付仍叫 M3J。

## 已确认的结论

这次包含两个问题：模型原始输出本身标点很少；程序原来的显示长度保护，又会把没有句末标点的连续内容留在原始解码片段接缝。代码没有针对 large-v3-turbo 的专门优化，也没有 base 降级分支。

不能把“turbo 一定有更多标点”作为本次结论。在同一份约 41 分钟音频、同一已有 whisper.cpp b5130 Vulkan、同样 en / 8 线程 / 无 initial prompt 下，实际完整重跑得到：

| 模型 | 实际推理进程时间 | 原始 SRT 段数 | 原始句末标点数量 | 原始逗号/分号/冒号数量 |
|---|---:|---:|---:|---:|
| ggml-base | 100.047 秒 | 350 | 25 | 0 |
| ggml-large-v3-turbo | 180.110 秒 | 340 | 2 | 0 |

两次均退出 0，stderr 明确 Vulkan0 / AMD Radeon RX 6900 XT。统计直接针对引擎原始输出，未经过程序分句；本例没有复现“turbo 标点比 base 多”。其他会议、语言、提示词、引擎配置会影响输出，不能从这一份样本推导所有场景或模型准确率排名。

另完整跑一次 base，唯一改变是去掉 `-ojf`，用时 96.125 秒；原始 SRT 与开启完整 token JSON 时 **SHA-256 完全相同**。因此本例少标点不是为了分句获取 token JSON 造成的。代码未强制 `-ml`，CLI 上限保留默认 0；没有模型名特殊分支。

官方资料提供背景而非本地质量验收：base 约 74M 参数，turbo 约 809M，turbo 是 large-v3 的优化版本；官方明确模型间存在速度/精度取舍，效果受语言与硬件等影响。此资料不保证某个录音的标点或分句一定更好。[OpenAI Whisper 官方说明](https://github.com/openai/whisper#available-models-and-languages)。锁定 b5130 CLI 的 `max_len` 默认 0，`-ml` 才显式改变字符上限；`-ojf` 是完整 JSON 输出参数。[whisper.cpp b5130 官方 CLI](https://github.com/ggml-org/whisper.cpp/blob/b5130/examples/cli/cli.cpp)。

## 旧程序问题的证据

用户指向的上一任务“本机完整重转写”对应本机 raw，共 350 段。全部 350 段的词 token 文字匹配、时码单调；并非异常 token 使分句失效。

旧程序处理后为 186 段，25 个句末标点一个没删。185 个段间边界中，20 为句末标点，22 为超过 1 秒的原段间隔；按旧保护逻辑依次分类，100 个受到 240 字符保护限制，43 个受到 30 秒保护限制。这些数字是规则分支分类，不等于每个边界经人工认定错误。

显示上限原本是为了避免一条字幕无限增长，但在少标点的原文里，只贪心合并完整原段会频繁停在任意解码段接缝。这是程序可以改进的部分。

## 本次实现

继续优先采用真实句末标点；到达 240 字符或 30 秒显示保护时，先回看本段已经存在的逗号/分号/冒号，或 **300–1000 ms、全文匹配且单调合法的词 token 间隙**，优先在这些候选边界收束。候选前至少已有 40 个字符与 4 秒，避免碎成很短的字幕。没有可证明的候选就保留原始片段边界，原段本身过长也不按字符均分。

词间停顿只在原文确有空白分隔时使用；英文子词、无空格 CJK 不能仅凭 token 时差被拆成词。千分数字、小数/时刻相关标点和无空格 ASCII 表达式保守回退；异常/缺失/不匹配 token 不用于重切。句间超过 1 秒、重叠、来源/说话人变化和 untimed 继续隔离。所有回听范围仍来自原 token/原段，质量保持 `approximate`。

没有补写标点、语义润色、添加文字、均分时码或改动解码参数。它减少任意接缝，不能承诺每条都是完整语义句。内部候选重新合并时保留原文真实分隔空白，已覆盖 José / mañana、双空格、tab、NBSP，避免 Unicode 词连成一词。密集 10000 个短时标点候选采用累计状态及 StringBuilder，避免二次复杂度。
