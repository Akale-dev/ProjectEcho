# 66｜M4、M5 规划说明与 M3H 后的调整评审

> 2026-10-04 编号更新：本文保留历史评审措辞。下文旧 M4/M5 及其 A/B/C 分期现分别对应 **M7 项目分析（暂缓）/M8 可选标签页**；旧 M6 为 M9。当前 M4–M6 是中文 ASR、同场说话人、可选双 ASR 复核，见[70](70_M4_M6_LOCAL_ASR_ROADMAP.md)。不得用本文旧 M4 提示直接启动现阶段工作；当前入口见[提示词索引](../prompts/README.md)。

评审日期：2026-10-03（Asia/Hong_Kong）。基线：当前工作区与 M3H-Final 交付记录。

本文是说明与建议，尚未修改正式里程碑、验收状态或产品实现。文中的“建议新增”“建议分期”均不表示已经采纳或完成。M4、M5 目前仍未实现，T41–T45 均为 NOT_RUN。

## 1. 结论与两阶段的关系

**M4 的目标值得保留，但需要重新细化数据、版本、人工确认和分析引擎合同；M5 保持可选，先验证浏览器采集可行性，再接入现有录音保存链路。**

| 阶段 | 用户实际得到什么 | 当前状态 | 本次判断 |
|---|---|---|---|
| M3 | 可回听、检索、校订的录音与多版本文字 | 已迭代至 M3H；验证范围与剩余限制见 STATUS | 为 M4 提供了更多可复用能力，也增加了版本选择等必须处理的情况 |
| M4 | 每条结论能查到原话的会议纪要，以及同一项目多场会议的变化记录 | 原规划、Schema 和验收条目存在；未有产品实现 | 优先做单会议证据与复核，再做自动生成和跨会议汇总 |
| M5 | 在同一 Chrome 实例中只采集明确选择的一个标签页 | 方案与验收条目存在；扩展、桥接未实现 | 是否推进取决于单标签隔离的真实需要和扩展安装条件 |

M4 位于文字之后，既可使用本程序录音，也可使用导入录音及文字。M5 位于音频入口，成功接入后继续使用现有保存、混音、导出和 M3 转写流程。两者不是必须依次完成的技术依赖。M5 不需要等 M4 才能做，M4 也不需要 M5。

M3H 的 263 项回归、包内 WPF 和 Vulkan 检查不能代替 M4 的内容可信度验收，也不能证明浏览器单标签采集可用。干净 Windows、长期双轨声学同步等旧录音验收缺口继续独立保留。

## 2. M4 原规划：来源可查的项目纪要

原始依据：[项目分析与证据链](08_PROJECT_ANALYSIS.md)、[M4 开发提示](../prompts/05_M4_PROJECT_ANALYSIS.txt)、[Analysis v1 Schema](../schemas/analysis.schema.json)。

### 2.1 计划产出哪些内容

| 内容 | 计划用途 | 必须遵守的边界 |
|---|---|---|
| 会议摘要 | 帮助快速理解讨论主题与结果 | 摘要是归纳，不冒充逐字稿；事实性结论需要来源支持 |
| 决策 | 记录明确同意的选择、取消或替代 | 区分建议、同意、否决、未解决；不能把“考虑一下”写成决定 |
| 备选方案 | 保存提出过但未采纳的路径 | 不能因为最后没再提，就推断已否决 |
| 行动事项 | 记录要做什么、由谁做、何时完成 | 未明确的负责人、截止日期保留为空；发言者不自动等于负责人 |
| 未决问题 | 保存仍待回答、确认的事项 | 下一次没提到，不自动变为已解决 |
| 风险 | 记录已指出的风险及其依据 | 不因会议安静或未再讨论而自动关闭 |
| 跨会变化 | 对照同一项目的多场会议，找出新增、变更与反转 | 保留历史及替代关系，不覆盖旧决策 |

每条结构化事项原本计划包含类型、正文、状态、负责人、日期、证据和复核状态。证据指向具体会议、具体转写版本、具体段落、原有时间范围及短引文。

有时间的证据可以定位到原录音；TXT/MD 等无时间文字只能定位段落，并显示“无时间信息”。外部字幕与模型生成时间的近似性质必须保留。程序不能根据句长补出精确时间，也不能把来源轨或 Speaker1 自动认定为真实姓名。

### 2.2 原规划中的人工确认与历史

自动产生的内容先保存为草稿，逐项修改和确认后才形成已复核版本。需要分清两件事：

- “会议是否明确同意了这个决定”是事项的业务状态。
- “用户是否核对过程序生成的这个条目”是人工复核状态。

程序识别到明确同意的原话，仍不等于用户已复核模型的归纳。

跨会发生反转时，新增决定并指向被替代的旧决定，保留两次证据。例如先讨论方案 A，后来明确改用 B，应能看到 A 的历史、B 的新依据及改变原因。没有新的完成证据，旧待办不得自动标成完成。

音频或文字中的命令只作为会议材料；其中的链接不自动打开，不执行代码，不自动发邮件、派任务或发送纪要。

### 2.3 建议的实际使用流程

以下是基于现有 M3 界面的交互建议，尚未实现：

1. 在会议库选中会议，再明确选择用于分析的转写版本。
2. 查看输入范围、来源警告和时间信息；未分类会议也能先做单会纪要。
3. 手工整理、导入分析草稿，或主动运行另行配置的本地分析引擎。
4. 查看按决策、任务、风险等分类的草稿；逐条打开原话和证据回听。
5. 修改并确认条目，保存新的复核版本。录音期间可以看文字，音频回听继续遵守现有禁播规则。
6. 明确归入项目后，选择同项目的会议和版本，生成项目变化草稿。
7. 按需导出本地纪要。建议首版支持可读 Markdown 和结构化 JSON；这是新增建议，不是现有功能。

当前 Whisper 接口完成的是语音转写。仓库没有可运行的 M4 文本分析引擎，也没有锁定分析模型、运行时或硬件要求。不能把随包 base 模型、Vulkan 可用或 ASR 提示词当作“纪要模型已经准备好”。

## 3. M3 多轮迭代后，M4 必须调整什么

### 3.1 复用现有能力，并补上新的边界

| 已有变化 | 给 M4 的帮助 | 需要调整的规划 |
|---|---|---|
| 外部录音、TXT/MD/SRT/VTT/项目 JSON 导入 | 不必重新建设导入流程 | 分析覆盖定时与无时间文字；导入日期不能当会议发生日期 |
| 多模型原稿、重复识别、人工子修订 | 可选择更可靠的文字作依据 | 每次分析冻结明确版本，不能默默切到“最新版本” |
| 原文、版本和段落标识 | 可以建立证据引用 | 分析还应保存所用修订文件的指纹并验证引用，避免引用错会或被改写后的内容 |
| SQLite 会议库与全文检索 | 可复用会议筛选和段落查找 | 数据库继续是可重建索引；分析正文和确认记录应有独立权威文件 |
| 项目归档仍是可编辑名称 | 已能按项目筛选 | 跨会分析需要稳定项目身份，不能只依赖相同名称，更不能把全部“未分类”汇总为同一项目 |
| 回听、字幕定位、百分秒显示 | 复用证据回看界面 | 显示到 0.01 秒不代表声学时间准确到 10ms；原质量标记继续展示 |
| 每会识别选项、提示词及默认快照 | 已有任务归属和设置保存经验 | 分析设置与 ASR 设置分开；保存本次输入与分析配置快照 |
| 每会 Log、后台任务归属 | 可以记录分析开始、取消、失败 | A 会议的后台结果不能覆盖 B；日志导出不得夹带完整分析提示词和会议原文 |
| 可恢复删除、归档修改、索引重建 | 已有资料生命周期 | 明确跨会分析在来源删除、改项目、恢复后的行为，防止缓存继续纳入已删除会议 |
| 现有 ASR 质量及长会限制 | 可以逐句人工校订后再分析 | 结构正确不等于内容正确；中文、数字、否定、多人和长会质量要独立验收 |

### 3.2 最应优先处理的六个问题

**一、固定分析使用的版本。**

同一场会议可能有 base 原稿、另一个模型的原稿和人工修订。M4 应让用户确认输入，记录实际版本及其指纹。新转写出现时，旧分析保持原依据，可提示“有新版本可供重新分析”，不能把旧证据链接自动指向新稿。跨会输入每场默认只选一个明确版本；多版本比较应是显式操作，避免把同一发言当成多次独立支持。

现有代码把文字修订保存在 reviewed 目录，但“保存过修订”并不证明全文已逐句校对。M4 不能据此自动认定每一句都可靠，更不能顺带把分析设为已复核。

**二、项目身份和会议时间需要更准确。**

当前项目是归档文字；建议新增独立的稳定项目 ID，名称可变，原会议目录不因归档搬动。单会分析允许没有项目；跨会分析必须明确选定项目及输入范围。已有同名项目是否合并要显式处理。

还应区分导入时间、实际会议日期及日期可信度。录音导入时通常不知道原会议日期；仅凭导入时间不能把“下周五”转换为某个日期，也不能可靠判断两场会议的先后。日期未知时保留原话和待确认状态，必要时由用户补充会议日期或选择顺序。

会议库目前以目录键区分副本，即使内部 meetingId 相同也可分别存在。M4 的证据解析须考虑这一点，不能只凭 meetingId 在整个数据根取第一场。建议在不改写原音频与旧转写的前提下，补充可随资料迁移的会议实例身份。

**三、补全 analysis 数据格式。**

现有 v1 Schema 是起点，但与文档及 M3H 实际情况存在以下差异：

| 当前不足 | 建议 |
|---|---|
| 文档要求逐项 reviewState，Schema 只有整个分析的 reviewState | 增加逐项确认、修改、排除及其记录，并明确整份文档何时算复核完成 |
| 输出写了“会议摘要”，Schema 的 item type 没有摘要或相应字段 | 定义独立摘要及其来源支持方式 |
| 缺少分析父版本、生成时间、引擎/模型/提示词版本和输入快照 | 增加可追溯的生成记录与不可覆盖版本 |
| evidence 有版本、段和时间，但没有时间质量及来源可用性 | 保留 untimed/approximate 等质量；来源缺失、损坏和有警告要分别表示 |
| owner/dueDate 只有结果值 | 对“谁负责”“日期如何得出”分别关联证据；缺少依据时仍为空 |
| supersedesId 是单一字符串，没有明确跨分析版本的解析范围 | 使用明确的旧分析/旧事项引用，校验同项目、存在性及无循环 |
| proposed/agreed 等无法表达任务实际完成、取消 | 将讨论状态、执行状态、人工复核状态分开；人工更新留下用户操作来源，不能伪造成会议原话 |
| required projectId 不区分未分类单会与跨会 | 显式定义单会/项目范围及未分类状态 |

不建议为了沿用旧 Schema 勉强塞字段。可在 M4A 定义兼容的新版分析格式，保留旧示例；本次评审未直接修改 Schema。

**四、先决定分析从哪里来。**

建议分清三个入口：手工建立条目、用户主动导入结构化草稿、可选本地文本生成。前两个入口先把证据与复核做实；本地生成作为 M4 正式能力继续实现，并单独选择、实测引擎和模型。

导入的分析也只能是待验证草稿。模型返回了 revisionId 或“已确认”字样，都不能直接相信；程序应逐项查找本地输入、校验段落与引文。不能解析的普通纪要可作为手工材料，但不能冒充已有证据链。

本地分析保持独立可取消任务，不在采集回调里运行。引擎和模型应事先准备并核对许可；正常使用不新增 Node/Python 或管理员前置条件。没有分析模型时，录音、导出、M3 和人工纪要仍可用。手动外部分析仍由用户自行上传，软件不新增云 API、密钥或自动外传。

**五、长会与跨会要明确覆盖了多少材料。**

不能简单取全文前若干字后显示“完整会议分析”，也不能只找几个关键词命中就声称覆盖项目历史。建议按原段落边界分批，保留每批输入清单、必要上下文和覆盖记录；最终汇总仍能追到原始转写，而不只引用中间摘要。

覆盖不完整、任务取消或某批失败时，应显示已处理范围，不能把部分结果发布成完整纪要。重叠分片、重复发言和同会多版本需要区别处理，不能靠全文相同句子直接删重。

目前没有完整三小时自然会议识别验收；M4 也需要独立测量长文本内存、耗时与关键事项遗漏。先使用合成或明确授权材料，绝不以短英文样本推定金融中文长会可用。

**六、补齐删除与引用失效规则。**

单会分析建议存放在该会议目录内，随会议可恢复删除和备份。项目汇总另存时，需要记录依赖关系。来源会议删除、撤出项目或损坏后，新分析不再使用它，旧分析明确显示来源状态，不能偷偷换一份文字维持“证据可用”。

跨会摘要可能保存了源文短引。删除会议时应提示这些派生内容仍可能存在，并提供明确的处理选择；不能一边说会议已删，一边无提示把其内容继续用于新检索和生成。

## 4. M4 建议分期与验收

以下 M4A/B/C 是建议拆分名称，尚未写入正式里程碑。

| 建议子阶段 | 用户可用成果 | 主要完成条件 |
|---|---|---|
| M4A：单会证据与复核 | 选择转写版本；手工/结构化导入草稿；逐项查看证据、修改、确认；保存和本地导出 | 新版数据合同；证据准确解析；原稿/旧分析不覆盖；无时间文字正确显示；取消与重开安全 |
| M4B：本地单会自动分析 | 对选定文字生成摘要、决策、任务、风险和问题草稿 | 锁定并实测独立文本引擎；输入覆盖、失败/取消、内容错误与人工复核全部可见 |
| M4C：项目跨会变化 | 对明确选择的同项目会议形成历史和变化草稿 | 稳定项目身份；每会版本与时间明确；替代关系、未完成事项、删除/改项目正确；避免旧错误累积 |

M4A 只是交付顺序的建议，完成它不能宣称原 M4 的自动纪要和跨会分析已经交付。

保留原验收 ID：T41（建议/负责人/日期）、T42（跨会反转和重跑 ASR）、T43（提示注入）。建议扩充这些场景，并新增必要条目：

- “并未决定”“不由 Alex 负责”“可以考虑”不能变成确定决定或分工；同名人物与不明年份不自动补齐。
- base 原稿、另一模型原稿、人工修订并存时，证据始终落在用户选中的准确版本。
- 每个证据引用和引文必须能从输入原文解析；不存在的段落、跨项目引用和循环替代关系拒绝发布为有效结果。
- 无时间文字、缺失原音频、有完整性警告的音频均有正确降级展示。
- 索引重建、改名、可恢复删除/恢复、重复会议副本不造成错引或跨项目混入。
- 用户修改任务状态与模型推断分别记录；取消/崩溃后保留旧版本，未完成输出不冒充成功。
- 关键数字、否定、金额单位、日期及任务遗漏做有标准答案的内容评估；指标阈值在模型选定前后明确制定，不能只测 JSON 能解析。

## 5. M5 原规划：可选的精确单标签页录音

原始依据：[网页 Zoom/Webex](05_BROWSER_CAPTURE.md)、[M5 开发提示](../prompts/06_M5_OPTIONAL_TAB.txt)。

### 5.1 它解决的问题

当前“从特定应用录音”属于进程树边界。专用 Chrome 使用独立 user-data-dir 有助于分开日常浏览器，但同一专用实例内多个有声标签仍可能一起进入捕获范围。

M5 的目标是在同一个 Chrome 实例中，用户明确选择会议标签页后，只把该标签页输出的声音交给 ProjectEcho。另一个标签页播放视频或音乐，不应混入该录音。

它只改变浏览器声音来源的范围，不等于分离某位参会者，不自动获得参会者真实身份，不改善原始发言质量，也不替代 Zoom/Webex 桌面客户端的录音路径。标签页内部本来播放的所有声音仍属于这个来源。

### 5.2 原规划包含的组成部分

| 部分 | 计划功能 |
|---|---|
| Manifest V3 扩展 | 用户主动点击后捕获所选标签；最小必要权限；不扫描普通浏览历史、不注入会议页面 |
| 听会声音回接 | 在采集标签音频的同时，让用户继续正常听会议 |
| 本机桥接 | 将浏览器音频传给桌面程序；限制到 loopback，配对认证、限定来源、限制消息和队列大小 |
| 音频与时钟协议 | 保存序号、帧数、浏览器时钟及其与桌面会话时钟的关系 |
| 断连和积压处理 | 显示异常与缺口，缓冲有界，不无限占用内存，不伪造连续音频 |
| 防重复录制 | 单标签模式不再同时录同一浏览器进程或输出端点 |
| 独立麦克风 | 仍由 Windows 录音引擎按明确同意采集；扩展不另开一份麦克风 |
| 可选分发 | 只有用户允许且组织允许时才安装；扩展失败不破坏无扩展版 |

### 5.3 本次核对的 Chrome 官方能力

截至本次查阅，官方文档仍要求用户调用扩展后才使用 tabCapture；捕获后需要显式音频回接才能继续听会。捕获可跨同一标签的导航持续，因此不能把换网页自动当作录音已停止。[Chrome tabCapture](https://developer.chrome.com/docs/extensions/reference/api/tabCapture)

官方提供 Chrome 116 起由 service worker 获取流标识、交给 offscreen document 使用的路线；仅把录音放在扩展弹窗里会随弹窗关闭而停止。因此应使用可持续的后台音频页面，并限定为音频用途。[Chrome 音频捕获指南](https://developer.chrome.com/docs/extensions/how-to/web-platform/screen-capture)

offscreen 的 AUDIO_PLAYBACK 原因在无播放 30 秒后可能关闭文档；官方录音示例采用 USER_MEDIA。实现时须选择与真实用途相符的原因，验证长静音及生命周期，不用人为噪声保活。[Chrome offscreen](https://developer.chrome.com/docs/extensions/reference/api/offscreen)

这些是文档核对结果，未安装扩展、未运行浏览器采集验证，不能记为 ProjectEcho M5 实测通过。

## 6. M3H 后，M5 应怎样调整

### 6.1 接入一套录音系统，新增清楚的来源类型

当前源码的 SourceMode 只有 ProcessTree 和 EndpointLoopback；不存在已实现的标签页来源。M5 需要增加明确的标签音频来源合同，复用一个 CaptureHost、分块原件、混音、导出、M3 与日志体系，不应另外建设一套独立会议库或只保存浏览器最终压缩文件。

但现有 Windows 采集包带 WASAPI device/QPC 字段。浏览器采样帧计数不能伪装为硬件 device position，浏览器 clock 也不能直接塞入 QPC 字段。需用带类型的来源时钟数据及版本化的存储/恢复合同，保留旧录音的读取路径。

桌面界面可在现有两种来源之外提供“从浏览器标签页录音”，显示已授权标签、连接状态、声音状态及独立 mic 状态。不强制整个录音界面重新设计。

### 6.2 暂停、恢复和停止是首要验证项

当前合同要求暂停真正停止采集。M5 不能只停止向桌面发送，或在收到 PCM 后丢弃，而浏览器仍持续捕获。

建议优先验证：暂停时停止标签媒体轨和采集处理，恢复浏览器正常听会；恢复录音时重新获取获准音频流，并建立新时钟段。如果当前浏览器要求重新点击扩展，就明确提供该步骤，不能绕过用户手势要求或提前承诺桌面一键恢复。

“正在暂停/停止”必须等待实际来源边界确认；正常停止还要排空截止前已获准的有效包，写盘完成后才显示“已保存”。需要定义从浏览器序号、帧偏移到 Host 写入水位的对应关系。不能按网络消息抵达时间粗暴丢掉队列尾部。

桥接或标签丢失后，应及时停止浏览器剩余采集，按已确认有效数据保存并明确故障状态；是否继续独立 mic 要在合同中预先定义。建议沿用明确的自动暂停/重新确认流程，不让界面停在“正常录制”却只剩一个来源。

### 6.3 把“听会回接”和“旧录音回放”区别写清

M5 需要允许当前授权标签流的实时音频回接，以保证用户听会；现有旧录音、字幕证据和导出试听的禁播规则继续有效。回接不是开放所有播放入口的理由。

应验证回接只有一条、停止或暂停后路由恢复、输出设备变化与耳机切换、没有进程/端点二次录制。麦克风可能收进扬声器回声的问题仍存在；单标签隔离不会消除声学回灌，也不提供会议软件 mute 同步。

M3H 的来源电平预览也不能直接套用：标签音频在用户授权采集前不应为了显示电平偷偷打开媒体流。连接检查与权限检查可以先做，真正的声音预览必须有明确动作和可见状态。

### 6.4 补足时钟、恢复和长期验证

建议协议保存会话/来源标识、段号、包序号、实际帧数、格式、浏览器原始时钟、时钟重置和缺口原因；另保存与桌面单调时钟的校准锚点及误差范围。单向消息到达时刻不能作为唯一依据。

恢复时只依靠磁盘上的原轨、时钟与边界记录重建时间轴，不能依赖仍活着的 AudioContext。队列积压、乱序、重复包、丢包、重新授权、采样率变化、休眠恢复都需要可观察处理。

保留原有两小时双轨同步目标及全时段、尾帧要求；借用既有 Windows 混音器之前必须证明它理解浏览器的新时钟数据。重采样本身不是长期同步的验收证据。

### 6.5 桥接仍应先做小样验证

本机 WebSocket 可以继续作为候选，但它还不是已经证实可部署的最终方案。先在实际 Chrome/Windows 和允许的组织环境验证连接、权限、音频页生命周期及关闭清理。只在单标签模式启用期间监听，不变成开机常驻服务。

认证至少绑定确切扩展身份、短时配对会话和单个录音任务；限制 loopback 地址、Origin/Host、消息长度、速率和队列。Origin 不能单独承担认证；WebSocket 也不能仅依靠 HTTP CORS 设置保护。token 不放 URL、文件名或普通日志，浏览器输入不得指定任意文件路径或执行命令。具体握手和本地应用身份校验在验证阶段评审。

Windows 的 native messaging 通常需要注册本机 host 的注册表位置。因此它可作为另行评估的选择，却不宜默认成为纯便携包前置条件；采用时须明确安装、更新和卸载范围，不能修改组织策略。[Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

### 6.6 精简首个 M5 版本的范围

建议先限定一个经验证的 Chrome 稳定版本范围、单个明确选择的标签、音频、一个活动录音会话。实际网页 Zoom 与 Webex 分别验证。Chrome 116 是相关 API 路线的能力起点，不应被写成推荐安装旧版或“116 以上全通过”。

先不承诺 Edge、无痕、多 profile、多标签同时混音、自动寻找会议、自动切换新标签或自动安装扩展。跨站导航、会议弹出新标签、转入桌面客户端、标签关闭/崩溃都要显示清楚的来源状态；建议首版在来源用途变化时要求重新确认，绝不跟随到更宽范围。

## 7. M5 建议分期、优先级与验收

以下名称同样只是建议：

| 建议子阶段 | 要得到的证据 | 通过之后才承诺什么 |
|---|---|---|
| M5A：授权后的可行性验证 | 同实例两个标签不同合成音；用户仍能听会；长静音、暂停/恢复、流关闭、桥接断连、时钟样本 | 当前目标环境可以进入产品接入，不等于日常版已经可用 |
| M5B：接入 CaptureHost | 独立原轨、时钟落盘、mic 边界、尾帧、崩溃恢复、混音/导出/转写兼容 | 新来源完成既有核心链路与回归 |
| M5C：网页场景及分发验证 | 真实 Chrome 网页 Zoom/Webex、目标设备、长期同步、安装/更新/移除和策略限制 | 只对实际版本、模式、设备组合声明支持 |

沿用 T44（标签隔离与听会）、T45（桥接认证、断连和有界缓冲），并补充测试：同实例目标/非目标声音、导航/关闭/新标签、暂停后无采集、恢复授权、停止前短尾标记、断连后停采、15 分钟静音、两小时 browser+mic 公共参考同步、磁盘不足、单实例与重复配对、无扩展版回归。涉及扩展安装、真实录音和 mic 的实际执行仍需符合用户明确授权。

**建议默认顺序：M3 数据与合同整理 → M4A → M4B → M4C；M5 根据单标签隔离需求单独安排。**

若日常主要使用桌面 Zoom/Webex 或导入录音，M4 的直接收益通常更大，这是基于当前用途的优先级判断。若必须在同一浏览器里同时开其他有声标签，且组织允许安装扩展，可以把 M5A 提前；它仍是可行性验证，不应直接许诺完整 M5。

M3 整理应聚焦实际数据合同、文档过期内容和分析输入质量，不等于再开启一轮界面重做。现有平台/长期同步/干净 Windows 的未验事项保持单独清单；M4 文件分析可以在隔离范围内推进，不能据此宣布录音现场验收完成。
